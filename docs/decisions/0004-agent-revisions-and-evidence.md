# 0004：受控修订、查询证据与反馈用量

日期：2026-10-06（Asia/Hong_Kong）。状态：设计冻结，待实现和验证；本记录不宣称 Agent、模型计费或修订恢复已经可用。

依据：[唯一现行总蓝图](../ORCA-Agent-Project-Blueprint.md)第 3～6、8～12、13.3、14 节，以及用户授权实施的阶段 B 方案第 3、4、5 节。适用范围是现有 Windows 本地底座上的首个 Agent；不新增科学方法、远程后端、常驻进程或第八个领域生命周期。

现有实现保留固定 Request/Plan、防止累计用量回退、不可变原始证据和 `orca-hf-2` 科学检查。下述变更必须保持这些保证，并通过专用入口实现新能力；不能通过放宽普通保存或删除检查完成兼容。

## 1. Request/Plan 修订及启动快照

**问题。** `Store.save_run` 当前禁止修改 Request/Plan 绑定，适合固定计划，但不能表达多轮补充、修复或成功反馈追加。`runner._recover` 从当前 Plan 找旧 Step，计划修订后可能无法恢复已启动尝试。Plan 也不能代表用户改变目标的权威。

**替代方案。** 允许普通 `save_run` 改版本，会让任意保存路径绕过目标和许可校验；原地修改 Plan/Step 会丢失启动条件；通用事务层、事件日志或新增修订对象生命周期超出当前问题范围。

**决定。**

- Request 保留原文、消息来源、条件来源、必需/可选目标、未决项及最低证据；未支持目标保留为缺口。Plan 可以调整取证路径，不能删除必需目标或降低规则。改变用户问题的 Request 修订必须追溯到用户消息；模型只能提出解释或澄清。许可与规范目标分别保存，模型提案不得扩大许可或预算。
- 普通 `save_run` 继续拒绝修改受保护绑定、许可、预算和期限。规划校验函数负责目标覆盖、工具能力、DAG、来源、条件、影响与允许改动；存储专用提交函数负责核对依据、不可变保存及激活，不承担科学判断。
- 专用提交在唯一 Run 协调者下比较 Request、Plan、许可版本和控制代次；最终激活时与短控制锁协调，保证新消息、暂停或取消不会被旧提案越过。过期提案拒绝或重新规划，不能只换版本标签。
- 先保存不可变修订及其决策依据，最后一次原子更新 `run.json` 的当前版本引用、累计修订用量和反馈处理引用。未被 Run 激活的修订只是孤立候选，不可执行。恢复只能在完整核验原提交依据和当前状态后重接同一候选，否则保留为失效候选；不能因文件存在而自动启动。
  实现中，新修订的完整 Request/Plan 保存在不可变 `decisions/<id>.json`，由 Run 内含内容指纹的决策引用激活。版本号查询只解析已激活的明确引用；初始/历史版本继续读取原文件。失效孤立候选因此不会占用下一正式版本号，缺失或篡改的已激活候选也不能回退到另一个同号文件。
- 科学预约在启动前冻结完整 Step、Request/Plan/许可版本、实际参数、输入指纹及具体消费绑定。冻结信息属于 Attempt 的局部执行快照，可写入现有不可变 `intent.json` 并由 Attempt 引用。恢复读取启动快照，不从新 Plan 拼出旧 Step。既有无快照记录仅可依据其原不可变版本恢复；证据不足时停止并报告，不能从当前值补造。
- 同一逻辑科学步骤的所有 Attempt 和 Result 均保留。已启动尝试不可改写输入，条件变化只影响当前适用性。初始 Plan 单独记录，不消耗自主修订次数；后续自主修订受冻结上限约束。用户补充、换 ID、暂停或恢复均不退款、不重置期限或用量。

**验收影响。** 拒绝普通保存越权、过期提案、删必需目标和降规则；证明用户修订后旧作业结果仍属于旧条件；覆盖“修订已写但未激活”“旧 Step 被修订移除后恢复”等窗口。重复恢复不产生第二次修订或追加执行。

## 2. 查询 Run 与统一 Tool 边界

**问题。** 现有 Run/Result 假定科学 Plan/Step/Attempt；初始化依赖 ORCA 环境，预约默认占用科学并发槽。纯查询需要保存来源与调用事实，但不能被伪造成科学计算。

**替代方案。** 为查询创建虚假 SP/Attempt 会污染科学成本与来源；绕开 Run 和 registry 的单独查询通道会失去一致的权限、预算和审计；新增 Query/Job 领域对象没有必要。

**决定。**

- Run 允许没有 Plan，科学启动预算可为零；即时只读调用作为 Run 内有界局部记录，关联 Result 和真实 Artifact 来源。科学执行仍必须绑定 Plan、Step、Attempt。导入副本、生成派生产物或形成下游依赖的分析建立明确 Plan/Step，不能借查询身份隐式执行。
- Tool 的参数 schema、输入角色、输出声明、检查、执行入口和实际影响来自唯一 registry；CLI、Agent 与历史查询使用相同校验。是否占用科学槽由经程序核验的 `execute_orca` 影响决定，不能信任模型提交的“只读”标签。只读查询不要求 ORCA 安装、doctor 成功或科学许可。
- 查询的 Result 分别保存提取操作事实和证据观察；读取成功只能满足对应查询目标，不能发布未经检查的科学端口。每次读取/消费核对 Artifact hash，路径、行号、视图版本、已知单位和未知条件随结果保存。
- 外部来源以用户登记的受控 source 引用解析，首版采用不可变副本。导入 Run 只证明本系统导入过程，不补造原运行、Attempt、时间、输入或费用。缺 JSON 只返回缺失及明确后处理需求；读取不得触发转换或重算。
- 历史缺省仍按旧语义读取；旧 Run 的零模型/修订预算继续为零，不能因新增字段默认值而获得权限或被原地迁移。

**验收影响。** 无 ORCA 环境且科学预算为零时完成查询；缺 JSON、部分导入、未知单位和 hash 变化均准确保留事实；原文件不变、科学/后处理启动为零。创建新产物或科学执行不能通过只读入口绕过许可。

## 3. 异类科学规则和具体消费绑定

**问题。** `_validate_execution_rules` 与 `calculation.revalidate` 对整个 Request 统一要求 HF 规则，阻止能量、查询与派生目标共存。`_validate_future_binding` 将生产者检查版本直接与消费者 Tool 版本比较，无法正确表达异类工具依赖。按某 Step 的最新成功选择输入也无法处理多尝试。

**替代方案。** 删除版本门禁会让旧证据自动升级；要求全链相同版本将不同物理量绑定为一个规则；按时间或“最新文件”选输入不具备稳定来源。

**决定。**

- 检查适用性按“本次 Tool、输入角色、输出及目标用途”判断。SP/Opt 继续使用 `orca-hf-2`；查询验证提取准确性；电子能差与有限采样分别使用自己的版本化验收规则，同时声明所需 HF 来源端口、规则和条件。
- 消费者注册定义声明前置条件和接受的生产者检查要求；规则名称不同既不自动拒绝，也不自动兼容。规划期可引用未来 `Step + port`，执行前必须固化具体 Run/Attempt/Result、输出端口、Artifact/hash、相关检查和条件；没有文件型输出时仍绑定数值所属 Result 及原始来源证据。
- 物理量、几何关系、原子映射、电子态和方法等按当前用途核验。允许 Request 明确的同体系不同几何电子能比较，不允许仅因单位相同比较任意体系；电子能差不能满足自由能目标。
- 历史 `orca-hf-1` 事实可读，但未经显式复验不能用于要求新规则的科学消费。复验通过统一读取/检查责任链形成带来源的新 Result，保留旧 Result 和检查，不改写旧原始证据。
- `supersedes_result_id` 继续仅服务同一尝试的未知执行补收链；普通重试、用途改变或检查升级使用明确来源/消费关联，不借该字段覆盖历史科学结论。

**验收影响。** 合法 HF 能量与派生目标混合计划通过；旧版、未知、条件不符及未合格来源被拒绝；多次尝试不能产生含糊选择。复验与恢复补收分别证明历史不变，现有严格优化/最终 SCF 片段检查不退化。

## 4. 结果反馈幂等与追加科学成本

**问题。** 每个新 Result 都须先影响目标与计划判断，文件保存窗口可能让同一反馈被重复处理；仅统计同 `logical_id` 重试会漏计初始计划之外的新科学步骤。

**替代方案。** 内存去重在恢复时失效；按最新时间判断无法证明同一决策；把每份新 Plan 都视为新任务会清零成本；固定自动追加科学步骤不构成成功反馈再规划。

**决定。**

- 由程序创建稳定的反馈/决策标识，绑定触发 Result、依据版本与控制代次；同时保存关联模型请求和候选动作。标识是 Run 内局部记录，不引入事件总线或独立 Feedback 生命周期。同一反馈在同一依据下的重放复用记录；用户修订使旧提案失效时，保留失效原因并对新依据重新评估。
- 所有新 Result 先更新事实、逐输出检查和目标适用性，再允许下游启动。必需目标证据充分时停止；没有新信息的轮询不调用模型。无模型结构化入口使用同一循环中的确定性策略。
- 新修订激活、对应反馈已处理标识与本次累计修订用量在同一次 Run 原子写入中发布。Result 已保存而 Run 未引用时，依据稳定调用/Attempt 和来源重接；反馈已生成但追加步骤未激活时，不重新发起模型请求或生成另一份追加动作来“补齐”。
- 以初始已激活 Plan 冻结科学步骤基线。重试和初始计划之外新增科学步骤都占用 `extra_orca_starts`，并受总科学启动上限约束；逻辑身份、原始基线归属及输入指纹共同防止换 ID 规避。追加额度在科学预约时占用，未知启动继续保守占用。
- 数据完整性不能证明是否已执行时，先对账且不启动副本。每份文件原子写入不等于跨文件事务；必要取消、对账、收集与确定性交付在独立有限期限内继续。

**验收影响。** 覆盖 Result 已写/Run 未引用、修订已写/Run 未激活、反馈已写/追加未绑定三类故障，并各恢复两次；断言模型、修订和科学预算不重算或漏算，未知执行不重复启动。左右加密、充分停止和耗尽反例分别检验行为，不能只测计划格式。

## 5. 模型 HTTP、token 与批次费用记录

**问题。** 模型调用具有不可回滚成本；超时或响应丢失不代表免费。SDK 隐式重试、格式纠正及多 Run 评测可能绕过计数，而凭据不得进入上下文、日志或产物。

**替代方案。** 仅成功响应后计费会漏掉失败请求；以字符数代替 token、按零缓存成本预约或假设未知为零均不保守；新增独立账务领域框架超出范围。

**决定。**

- 使用 Run 内局部模型调用记录，区分逻辑请求、提案纠正和每次实际 HTTP 发送。关闭 SDK 隐式重试；401/权限失败不自动重试。允许的显式传输重试及纠正分别受子上限、HTTP 总数、token 总数及 Run 剩余期限约束。
- 每次 HTTP 发送前，先持久化稳定调用身份、请求次数、输入/输出 token 保守上界及费用预约。输入上界来自经验证计数方式或可证明的保守估计，不能直接用字符数替代；无法证明余额足够时不发送。
- 调用完成后追加响应摘要/hash、供应商请求标识、实际请求/响应模型、可获知用量、时间和错误类别。保存 Request/Plan/许可依据版本、控制代次、提示模板和 SDK 版本、非敏感参数。API 别名不表示权重版本固定。
- 已知用量可以结算该预约的保守剩余额度，但历史实际发送次数与已确认消耗只增不减；预约、已知消耗和未知占用分别表达。超时、响应丢失、usage 缺失或崩溃窗口保持未知与保守占用，恢复不得标成零或盲目重发。
- 验收批次使用局部清单及带短锁的共享累计文件，所有参考、正式评测和开发探通的 Run 均绑定同一批次身份。发送前同时满足 Run 与批次限额；跨文件预约不能完整对账时保留占用并停止新增发送，不因新 Run/新会话漏账。不创建生产 Batch/Billing 对象。
- 批次 ORCA 分类在启动前唯一固定；独立参考、正式联合评测、开发探通各自子额度及总额均检查。后续引用开发证据不能改标签释放额度。模型计价依据、币种、生效/核验日期及来源随启用 profile 冻结，费用按保守未优惠价格预约；具体值见验收配置，缺失价格或模型环境时标为尚不可执行。
- key 只从 `DEEPSEEK_API_KEY` 读取。持久化摘要/hash针对排除认证信息的规范请求内容；不保存 key、认证头或可能带凭据的原始异常。响应与工具内容按不可信数据处理。

**验收影响。** 离线 fake client 验证每次重发计数、格式/语义纠正上限、截断/空响应/无 usage、超时未知占用、额度不足零发送、恢复不清零、跨 Run 批次限额及脱敏。真实模型与联合测试分别显式启用；缺 key 不使离线 CI 联网，不用模拟结果替代真实通过。

## 6. 实施和验证边界

本记录只冻结上述最小契约。现有 models/store/runner/registry 尚未因本记录而获得新行为，模型 profile、SDK 锁定、计价快照、独立参考和正式评测分别以实际产物为准。后续按阶段 B 方案顺序实现，每项同时增加定向回归；只有通过真实用例才更新能力为已实现，交付后仍等待用户验收。

方案与蓝图相关强制原则未发现实质冲突。方案文首的“只交付执行方案”及“未来实施”描述的是原方案交付状态；用户当前明确要求实施后，按其任务依赖推进，但这不授权静默扩大科学范围、增加预算或开放远程能力。
