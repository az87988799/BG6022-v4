# Code as Tools：受控任务执行、薄 SDK 与统一 ORCA 入口

日期：2026-10-18（Asia/Hong_Kong）。状态：实施步骤 2；实际兼容性、验证结果和限制以本次交付记录为准。步骤 1 已由用户明确验收通过。

## 问题与范围

原有执行链只承载带几何输入的 SP/Opt。它把每次尝试都计为 ORCA 启动，所有结果都进入固定 HF 检查器，并只管理单个计算的 JobObject。直接把 Python 塞入该链会误计预算，或者在等待 SDK 请求时因持有环境额度而无法启动内部 ORCA。为 Python 和 ORCA 分别建立独立的 1024 MB JobObject 则不能保证二者累计内存上限。

用户仅授权按 [专项方案](../CODE-AS-TOOLS-IMPLEMENTATION-PLAN.md) 实施步骤 2。此次建设动态代码及原生输入执行底座，不推进真实模型生成代码、自然语言交付、多计算算法、检查点恢复、跨任务冻结或正式矩阵验收。开发者编写的烟测不计作 Agent 自主能力证据。

## 选择与替代

| 选择 | 结果 |
| --- | --- |
| Python 直接启动 ORCA、读取产品 Store 或调用 CLI | 拒绝；绕过许可、预算、唯一协调者和原始证据边界 |
| Python 层替换 `subprocess` 或只用 JobObject | 拒绝；不能证明真实文件和网络隔离 |
| 每次 SDK 请求另开 Agent/Run/协调者与环境额度 | 拒绝；增加生命周期，可能死锁、重复启动和重置预算 |
| 当前协调者处理受控 IPC，复用同一 ORCA Tool 入口和累计预算 | 采用；SDK 只传输请求与回执，不包含科学求解算法 |
| 一次 Python 尝试在本步完成任意多次 ORCA 调用 | 暂不启用；每次 Python 尝试最多一次新内部调用，多次计算、检查点与反馈控制留待步骤 4 |

实际采用 Windows LPAC（Less Privileged AppContainer），启动前检查内核 token 与访问检查结果，普通 AppContainer 被拒绝。仅授予 CPython 初始化所需的固定 `registryRead` capability，不授予网络、COM 或广泛文件访问能力。它只开放 ACL 明确允许该 capability 的注册表资源；真实 HKCU 凭据哨兵仍被拒绝。每次创建独立 profile，并禁止任务访问 profile 自带存储。正常退出删除 profile；协调者硬崩溃可能留下 profile，持久执行身份记录 profile 名称与 SID，自动清理和内部回执恢复留待后续步骤。

Python、ORCA、科学库、MPI 与 IPC 各自保留真实进程证据；任一必要限制无法执行即拒绝启动。不能因兼容性失败回退到宿主无隔离进程。JobObject 承担进程树资源、期限、取消与协调者消失后的清理，不能代替文件/网络访问控制。

Python 通过内核 child-process policy 禁止新建子进程，使用 detached 启动以避免隐式控制台子进程；原生 ORCA 允许受相同 LPAC/Job 约束的必要助手，使用隐藏控制台以保留助手 stdout/stderr。主程序以准确绝对路径选择，`argv0` 则校验后传入相对路径，让 ORCA 的命令解释器可访问私有助手，不扩大宿主祖先目录 ACL。系统 `cmd.exe` 属于显式记录的 Windows 运行依赖；私有副本用于固定字节记录，不把它描述为已观测到的唯一命令解释器路径。

当前 MS-MPI 能启动受管工作进程，但真实 ORCA 四核 SP/Opt 和独立 `MPI_Init` 均失败；官方共享内存配置也未通过。因此统一入口在启动前拒绝核数大于 1 的请求，明确串行请求可执行，不自动改写原请求。选择继续交付已验证的串行底座并保留 MPI 阻塞；未选择放宽网络 capability、启用宿主 MPI 服务或无隔离运行。其他隔离平台、MPI 替代实现或精确 IPC 例外均需另行设计和验证，本次没有实施。

## 执行与记录契约

1. **同一七对象体系。** Python 和直接 ORCA 使用现有 Run 内的 Attempt 局部记录，明确 `execution_kind`；历史缺该字段的尝试保持原 ORCA 语义。几何只对既有科学适配器必需；生成任务绑定代码 Artifact、hash 和输入 manifest，消费前再次校验授权和来源。
2. **原始证据与写目录分离。** 任务获得必要输入副本、经过选择的运行库、独立写目录及受控 IPC。归档、Store、许可、预算和启动事实不属于任务写范围。运行环境采用显式允许列表，不把宿主环境变量与凭据传给任务。运行库不通过 editable 安装路径暴露产品源码。
3. **一个资源管理边界。** Python 先持有环境总量租约。由协调者启动的内部 ORCA 加入父级资源 Job，Python 等待时仍计入总内存和期限；内部计算不申请第二份环境总量租约。当前仍拒绝并发配置大于 1。进程启动采用不可继承 Job 控制句柄和明确的继承句柄列表；任务不能通过继承句柄改变管理边界。
4. **先持久化，再执行。** Python 尝试消耗尝试/代码重试预算，不误计 ORCA 启动。内部调用在启动前持久化稳定请求键、输入指纹、父尝试、输入代码/manifest、目标条件、工作量和启动预留。实际创建进程的身份只计一次实际 ORCA 启动。总资源由父 Job 统计，子回执中的资源事实不重复累加到 Run。
5. **有限内部调用。** 每次 Python 尝试最多一个新内部 ORCA 请求。同键不同输入拒绝；同键未完成或状态未知拒绝再次启动，先对账。Store 可识别已有同键同输入记录，证据入口可只读查看；本步 SDK 明确拒绝第二次调用与任务重放，回执复用和检查点留待步骤 4。回执不能删除或改写已完成事实。重新导入同内容 Artifact 或更换代码引用 ID 不改变代码/输入指纹。
6. **统一输入和执行。** OPI 生成的输入、直接原生输入与 SDK 请求使用同一 ORCA 执行入口。原生输入校验关注依赖、路径、资源、内部工作量及执行影响，不把一般方法名称作为科学支持白名单。无法确认可管理的多作业、外部程序或未知执行影响返回具体拒绝原因。输入校验不替代操作系统隔离。
7. **分别判断事实与科学资格。** 通用执行按实际存在的文件归档，缺少固定 JSON 不把整个操作判为失败，也不隐式运行转换器。既有 SP/Opt 保留原检查责任链与范围；通用输入和脚本结果不因进程成功或自报 `passed` 获得 QualifiedOutput。通用交付和新性质检查不在本步扩展。

## 验收影响

定向单元测试须证明授权/hash/路径检查在预算占用前发生、Python 不冒充 ORCA 成本、内部调用沿用父租约、预留与实际启动分别记账、未知状态不能重试、回执与累计预算不清零。以上测试不代替操作系统证据。

真实 Windows 验证须独立覆盖动态 Python 处理输入、必要库导入、SDK 最小调用与真实 ORCA、文件/凭据/网络拒绝、路径重定向、直接启动绕过、内存超限、超时与取消。应记录 MPI 兼容性与实测资源参数；若本步没有支持某种并行运行，必须明确拒绝并披露，不宣称并行链通过。原始代码、输入、输出、进程身份、资源和真实失败均保存索引。缺失项标记未验证，环境阻塞不得写为完成。
