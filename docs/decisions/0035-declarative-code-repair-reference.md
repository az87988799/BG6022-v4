# 0035：显式引用冻结步骤的代码修复提案

日期：2026-10-19。范围：Code as Tools 步骤 3 的已有代码错误修复，不推进多计算、恢复或后续步骤。依据总蓝图 P05/P06/P07/P14/P17 与第 10.6 节；用户要求修复问题、定向验证后交付，明确不再做全量回归。

## 问题与选择

live037 在 v56 上真实执行完整首版 Python，并在首个 SDK 前触发受控 NameError。模型自行写出新代码，但重复抄写冻结 Step 时提交了 retained 多余字段、互斥 Goal 路由和改动输入 manifest，修订未获执行，终局 failed/partial。原失败和未执行代码保留，不能算修复成功。

继续增加文字纠正已不能充分避免重复填写出错；放宽输入/条件/依赖冻结会改变任务；由开发者修脚本不能证明产品能力。因此新增一个局部、明确的 Plan 提案形态：`{key, repair_of, code}`。模型选择一个新的 Step key、一个已有失败 Step 的 ID，以及已完成写入的新 CodeRef。程序按这个明确引用复制可信的冻结任务字段，仅替换新 Step ID 和 CodeRef，保留 logical_id。这与既有 `{key: existing_step_id}` 显式复用的原则一致，不由程序决定修法、编写代码、选择科学条件或暗中追加依赖。

## 不可放宽的契约

- 只允许代码授权 Run，且引用必须对应本 Run 同逻辑任务最新已结算、确有 Result 的失败或超时 Python Attempt；缺失、未知、运行中、成功或有更新尝试的旧引用均拒绝。
- 使用独立闭合提案类型，不能混入 tool、logical_key、inputs、conditions、depends_on 等覆盖字段。旧完整 ProposedStep 形态保持兼容。
- 从 Attempt 的已冻结 Step 复制，不从模型提供的副本或不可信工具正文复制；新 key 不得复用历史 Step ID。
- 原输入 manifest、体系、条件、目的、观察声明和依赖逐字段不变；依赖闭包仍须由模型显式列在 Plan 中。Goal 路由仍由模型明确提交，原物理量与最低证据校验不变。
- materialize 只形成候选，不执行；仍经过既有 validate_revision、Python 修复、Artifact/hash/权限、预算和 Tool 执行校验。相同代码、错误来源、无剩余额度和未知执行继续拒绝。
- 不新增 Tool、运行时领域生命周期、任务求解器、解析器或科学资格；不改变任何历史 Run、执行后端或累计预算。
- 代码授权上下文从同一提案类型提供此形态及简短说明；非代码上下文不展示未授权分支，保持旧 schema 语义和容量。

## 验证与交付条件

定向验证覆盖成功展开、完整冻结字段相等、移出当前 Plan 的历史失败引用、明确依赖、错误/过期引用、混入覆盖字段、原权限/重试/Artifact 门禁、旧形态兼容与非代码容量。测试或纯内存重放只证明接口，不能代替真实模型成功。

新候选冻结后进行一次受控真实修复复验；采用前瞻 v5 请求，仅将 v4 中强制旧 logical_key 字段的提交表述改为保留原 logical_id、按当前 schema 明确引用失败 Step 与新 CodeRef 或合法完整修订；沿用原科学任务、人工故障说明、科学核验方法和预算，不把旧失败改记成功。原文 live035 仍保留 v55 身份，不冒充新候选重复。无论结果如何保留实际回执、完整代码差异、成本和限制；若没有成功重跑及完整交付，不宣称修复闭环完成。
