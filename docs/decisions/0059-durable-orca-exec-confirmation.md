# 短寿命 ORCA 的可信启动确认

日期：2026-10-21。范围来自用户持续真实测试、定位并修复底层阻碍的授权。

## 问题与替代方案

H1 开发候选 a004 的后两次 ORCA 在输入解析阶段迅速退出。宿主先经 Docker 释放启动 gate，再以另一 Docker 调用读取 `/proc/PID/exe`；进程可在两次调用之间结束。原回执因此保留 `unconfirmed`，实际用量账本却只累计已观察到的启动。原输出和未知启动事实不能被改写为未启动。

增加轮询频率不能消除竞态；根据 stdout、进程名或任务目录中的自报 JSON 判定启动会把数据当作执行证明。ptrace 的 exec 停机握手可以保留 inode 观察，但引入额外系统调用与父子进程管理，本轮不采用。

## 决定

1. 固定镜像中的可信 supervisor 通过 CPython `subprocess.Popen` 的 exec 错误管道启动固定的只读 ORCA 路径、参数及受控环境。child 在可信 pre-exec 阶段保留原 PID/start ticks 的 gate；无 shell、无用户 pre-exec 代码。exec 失败明确报错；无法区分 exec 前死亡的情况保持未知。
2. 启动确认通过原 Docker launch transport 的专用受控通道返回。ORCA 的 stdout/stderr 指向任务文件，其他描述符关闭；任务文件不能充当确认回执。宿主绑定原 gate 身份、固定可执行文件身份、当前 launch/container 并归档原始传输，再持久化实际启动事实。保留原 `/proc/exe` 证明及新方法的精确版本，不把不同证明标为同一种。
3. 更换 helper 必须离线重建并冻结新的镜像和 manifest。沿用原环境根、并发租约、4 核/1024 MB、无网络、能力清空和只读运行时。旧候选和历史 Run 保留原镜像、原状态与费用，不能自动迁移。
4. 原 a004 的两次未确认启动继续保守占用预约，并以追加对账说明补入开发累计账本，不修改原 outcome。操作已确定终止与实际启动次数未知分别报告，不能把后者当作零。

## 验证与限制

只验证该执行边界：exec 成功、快速失败、exec 本身失败、信号/不完整或伪造回执、恢复、真实短 ORCA 与正常四核 ORCA。模型任务随后使用新不可变候选测试。不运行无关全量回归，不以构建成功或离线测试代替真实 ORCA/LLM 证据。CPU 采样下界和磁盘配额等原有限制保留。
