## 问题与证据

候选 `repair-cycle-20261008-development-3` / `84f42ac` 的 N06、V06 各自通过，V07 `array-location` 失败。V07 的初始 Plan 包含正确的类型化数组路径；实际只执行了字段发现。第二答同时提交 `step_id`、`tool`、`parameters`，将 effect `read_registered_artifact` 当成 Tool 名，并漏掉 `Dipole_Moment` 后的数组索引。原发送上下文保存了正确的 Tool 名、Step 路径、两种互斥调用形状；这不是底层 reader 读取错误，也不是来源被删。

程序拒绝混合形状是正确行为。两次 HTTP 实耗 6697 tokens，剩余 25303。原纠正请求上界 11662 输入加 2000 输出，再保留最终交付 12000，共需 25662，差 359；调用次数、轮次和时间均仍充足。保守预约禁止了纠正，随后保存确定性部分交付，没有被接受的模型最终回答。旧失败与消耗保持不变。

紧凑投影会省去可直接复制的 Step 调用例子，留下结构 schema 与分散的 ID；Tool 字段的 schema 又只是任意字符串。已有文字明确禁止混合形状和使用 effect 名，仅增加同义提示不足以作为修补。

另有可修复的程序路径：Context 选择首个满足单请求上限与当前余额的投影，尚未计入已经要求保留的最终回答；发送守卫加入该预留后才拒绝，已有更紧凑投影没有机会尝试。将未来预留纳入候选选择，可以复用现有编码继续压缩，无需另建压缩协议或减少预留。

## 局部选择与边界

从现有 ready Step 集合和只读 Tool 定义生成调用字段的具体枚举，继续使用同一 `call_tool` 两种互斥形状。默认通用 schema 与历史只读重建保持兼容。当前只读反馈保留可直接复制的 Step 调用参数；Request 若已声明查询顺序，则例子按该顺序指向尚未完成且就绪的目标。例子只帮助模型选择，不替模型执行、不改 Plan、不授予权限。

只有 schema 中的 Step ID 枚举与输入 pending 列表完全相等、且原生调用例子确实指向其中一个 ID 时，紧凑显示省去 `CONTROL` 内同一列表的第三份副本。完整 ID 枚举、原生例子和 Plan 参数仍可见，输入 control 不变，发送/执行守卫继续使用实际 ready 集合。

保留即时只读调用能力、完整类型化路径、当前所有目标及来源。执行时仍由现有 Step/Tool/许可检查确定是否合法，不把枚举或提示当作授权。对实际纠正上下文测量总预约，必要去重必须保持事实可恢复；不放宽单 Run 或单请求上限，不用合成回答证明真实通过。

当前发送快照的候选投影同时检查本次预约与未来终止 tokens。首个投影不能同时容纳时尝试既有下一层；全部都不能容纳时仍可返回最紧的只读投影，实际发送守卫保持原预算失败，且在预约前拒绝。没有当前发送快照的历史只读重建保持原选择规则。候选组装不发送 HTTP、不改 Run 或累计用量。

无创建/修订 Plan 动作的反馈不再携带 Plan 构造提示。仅对与同一调用形状定义逐字段相等的程序纠正，展示时省去系统提示中已有的重复文字，保留参数路径及全部互斥字段集，持久拒绝原文不变。有限字符串枚举的 schema 省去其已隐含的字符串类型；不是删验收条件。
