# Code as Tools：本地 WSL2/Linux 容器执行适配

日期：2026-10-18（Asia/Hong_Kong）。状态：已按用户授权实现步骤 2 的最小容器适配，最终生产镜像已有真实 SDK/四核 OPI、隔离、资源与生命周期开发验证，详见 [续验报告](../acceptance/code-as-tools-step2-linux/report.md)，等待用户验收。初始 MPI、边界、OOM 与四核 ORCA 探测已有真实证据；它们不替代最终生产版本的隔离、SDK 和生命周期验收。

## 问题与决定范围

[0032](0032-managed-task-execution.md) 所记录的 Windows LPAC 路径已取得 Python、必要科学库、受控 IPC 与串行 ORCA 证据，但 MS-MPI 的真实 `MPI_Init` 和四核 ORCA 仍受阻。Windows 分支继续明确拒绝并行请求，保留失败记录，不把四核请求改为串行请求。

用户随后明确选择评估本地 WSL2/Linux 容器方案，以解决步骤 2 的隔离与 MPI 兼容性问题。本决定落实[总蓝图第 7.3、10.1—10.4、14.1 节](../ORCA-Agent-Project-Blueprint.md)及[专项方案步骤 2](../CODE-AS-TOOLS-IMPLEMENTATION-PLAN.md)关于真实隔离、统一执行、累计资源和失败替代决策的要求；平台变化不能降低这些要求。

本次先完成有界环境与 MPI 探测，取得四核 ORCA 与聚合 OOM 事实后，才实施 `backends/container.py`、镜像固定辅助程序及现有 Tool 入口的局部适配。没有引入通用容器框架、第二协调者、新对象生命周期或远程调度平台，也不推进步骤 3—7。开发者编写的 Linux 探测不计作真实模型生成代码或自主科学任务证据。Windows 既有实现、验收事实和旧 Run 不因本决定被覆盖或自动迁移。

## 替代方案

| 方案 | 本次决定及原因 |
| --- | --- |
| 保留 Windows LPAC 串行路径，继续明确报告并行阻塞 | 保留其已验证能力和历史事实；不能据此宣称默认四核配置通过 |
| 放宽 Windows 网络能力、调用宿主 MPI 服务，或脱离隔离启动 | 不采用；尚无保持原访问边界的实测证明，不作为兼容性回退 |
| 仅将程序放入 WSL2，直接执行在用户常用发行版中 | 不作为任务隔离方案；仍须证明文件、凭据、网络、执行与资源边界 |
| 本地 WSL2 内采用受限 Linux 容器，先验证 MPI 与隔离条件 | 已按初始探测证据实施最小适配；最终生产验证证据及适用限制见续验报告；验收要求如下 |
| 立即迁移全部执行逻辑或建设多后端平台 | 不采用；先暴露环境阻塞，避免围绕未经验证的平台建立空抽象 |

“容器”在此是待验证的执行边界，不是安全或兼容性结论。最终采用的运行时、内核、发行版、权限模型和清理机制以实际证据固定，不由名称推定。

## 首轮环境与 MPI 验证

首轮探测记录 Windows/WSL2 版本、发行版与内核、容器运行时及实际 cgroup 控制器。检查已有环境，按需准备专用运行目录和可信运行依赖；不把用户常用 WSL 目录、工程、凭据或其他容器内容作为任务镜像构建上下文。

可信部署流程准备 Linux 原生 ORCA、与其兼容的 MPI、固定 CPython、OPI 和必要科学库，记录来源、版本、依赖锁、安装包 hash、镜像内容摘要及适用许可证条件。Windows ORCA/MS-MPI 安装不能当作 Linux 兼容性证明。镜像以不可变 digest 选择，不能以浮动标签或任务运行时自动安装依赖替代冻结。ORCA 安装包及含其内容的私有镜像不因验证而公开发布；所需合法安装介质缺失时保留环境阻塞事实。

构建和可信依赖获取与任务执行分开记录。任务运行不继承下载凭据、代理、宿主环境或包管理权限，不执行网络安装，也不能修改镜像、运行时策略或后续执行许可。

在明确期限、进程数和资源上限下，依次取得以下独立事实；前一必要条件失败时停止依赖它的探测，不自动放宽限制：

1. 运行时真实提供所需 namespace、非特权身份、只读根文件系统和可核验的 cgroup 控制器。
2. 固定 Linux MPI 在无宿主/外部网络的候选边界内完成四进程初始化、通信和退出，保留每个 rank 与父子进程身份及 stdout/stderr。
3. 在相同限制下运行最小真实四核 ORCA 输入，保存输入、程序及 MPI 版本、资源记录和原始输出；分别判断进程退出与原有科学检查结果。
4. 核对真实文件/凭据/网络拒绝与资源控制，不以 MPI 成功推定隔离成功，也不以容器参数显示值代替内核和进程证据。

首轮探测成功只允许继续完善本步骤所需的最小适配；不等于 SDK 链路或底座完整验收通过。任一阻塞须给出实际命令或配置、返回状态与证据索引，不用模拟程序的成功结果替代 MPI 或 ORCA 事实。

## 已实现的最小适配与待验证范围

`ExecutionConfiguration` 是 Run 配置的局部类型。新 Run 配置版本 2 明确冻结 `backend`；Linux 还必须提供不可变 `sha256:` 镜像 ID、规范 JSON manifest 的 SHA-256、Docker context 和可信宿主 Docker 路径。版本 1 或更早缺配置的历史 Run 固定解释为 Windows，不能被当前默认值迁移或扩大许可。环境读取统一在 doctor 中核对镜像、manifest 与 daemon 身份；创建意图及实际准备再次比较 daemon，不自动构建、拉取或更换镜像。镜像 helper/过滤策略与本地后端版本不一致时拒绝新执行，历史对账仅检查已记录身份。

一个 Attempt 使用一个容器和一个聚合 cgroup；Python 与内部 ORCA 共用其 CPU/内存/期限及既有环境租约。镜像内 UID 10001 运行任务 Python，UID 10002 运行 ORCA/MPI，UID 10003 运行 PID 1 心跳/期限维护与固定管理操作。无 capability 的 UID 0 辅助程序仅处理固定输入、请求/响应与启动门；它不提供任务可调用的命令接口。任务 Python 编译前由固定 bootstrap 安装 seccomp：禁止 exec、fork/独立进程、网络、跨进程访问和可逃逸 namespace 操作，只允许满足固定 flags 的线程。ORCA 目录对任务 UID 不可遍历；使用不同 UID 的目的还包括防止任务改写原生输入、回执和生命周期文件。

每次尝试创建独立持久卷，预先固定各目录所有者与访问模式；宿主通过受限 Docker context、固定 helper 和有界字节协议传输。卷中的任务数据不覆盖宿主原始输入，收集路径拒绝 POSIX 越界以及 Windows 盘符、ADS、设备名、重解析点和名称别名。已准备的工作负载先等待不可由任务写入的启动门，宿主持久化身份、预算和实际启动记录并最后复核控制状态后才放行。内部 ORCA 每次 Python 尝试仍最多一次，不建立第二协调者或独立租约。

PID 1 按总期限和宿主心跳结束容器，任务不能续期；进程树终止仍须实际对账。原容器结束后需要收集时，固定收集容器挂载同一卷只读，设独立资源和自身期限，启动前保存身份，按父 nonce 标记。只有原容器及其派生收集容器都确认终止才释放租约；收集或终止回执未知则保留占用。输出超限、路径拒绝或复制中断保留卷、部分原始传输及结构化错误，不伪造完整归档。

运行库的选型、离线 wheel 锁、清单生成和部署入口位于 `scripts/container_runtime/`。固定 CPython 3.11.2、OPI 2.0.0、ORCA 6.1.1、Open MPI 4.1.8 及必要科学库；实际版本、关键程序/辅助源码 hash、许可证材料和镜像内容身份共同记录。第一生产镜像的有限库/seccomp 探测与最终修订 helper 的验收必须分开，后续 helper 补丁使镜像身份变化时需要重新构建和验证，不能延用前一镜像的全部通过结论。

已知限制：当前 CPU 记录是最后成功 cgroup 观察的下界，标为成本不完整；独立收集容器的 CPU 成本也未完整计入，不能声称精确端到端成本。持久卷没有每 Attempt 的磁盘硬配额；传输/归档的文件数、单文件与总字节预算不是写盘硬限制，超额工作文件及磁盘耗尽仍须如实报告。初始探针与离线单元测试不能替代最终镜像上的资源竞争、取消、硬退出、IPC 绕过和 SDK→真实四核 ORCA 测试。

## 生产验收仍须满足的边界

### 文件、权限与受控执行

任务只看到固定运行库、经 hash 核验的输入副本、独立写目录及有界 IPC。源码、Store、原始 Artifact、许可/预算/启动记录、用户主目录、SSH/模型/云凭据及宿主文件系统不得挂载或通过路径重定向访问。输入和运行库只读；任务输出、临时目录与 IPC 写权限分别限定。共享内存和临时写空间须有额度并纳入实际资源记录。

容器使用非特权任务身份、最小 capability、禁止提权、受限系统调用与只读根文件系统；不使用 privileged、宿主 PID/IPC/network namespace、宿主设备或可写 cgroup 控制文件作为兼容性捷径。具体策略必须与 ORCA/MPI 一起实测。Docker 的运行选项提供这些配置入口，但默认容器本身不是本项目边界已落实的证明。[Docker 运行参考](https://docs.docker.com/engine/containers/run/)

任务内不提供 Docker/Podman/containerd socket、WSL 控制入口、宿主执行凭据或任意命令代理。可信协调者如使用运行时 CLI/API，只能根据已校验的固定结构创建受限执行，模型和脚本不能给它传递宿主 shell、挂载、镜像、特权或资源覆盖参数。Docker daemon 的控制权限属于可信管理边界，不能交给任务。[Docker Engine 安全说明](https://docs.docker.com/engine/security/)

WSL 的 Windows 自动挂载和互操作必须作为单独检查项：任务不可经 `/mnt/c`、`/mnt/wsl`、互操作 socket、Windows PATH 或类似入口访问宿主。优先使专用任务环境不暴露这些入口；不因容器探测而悄悄改写用户其他发行版或全局 WSL 配置。WSL 的自动挂载与互操作有独立配置项，关闭其中一项不能作为全部越界通道被禁用的证明。[WSL 配置文档](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)

Python 仍不能绕过 SDK 直接启动 ORCA。将 Python 与 ORCA 放进同一镜像、移除 Docker socket 或隐藏 SDK 名称都不独立证明这一点；上述 UID、目录权限和 seccomp 的组合必须在最终镜像实测。两者处于单一容器资源边界，不引入额外 Run、独立科学协调者或各自一份总内存配额。

### 网络与 IPC

任务不使用 host 网络、不发布端口、不连接宿主控制服务或外部网络，也不继承宿主代理。优先验证 `network none` 类私有网络 namespace。Docker 的 `none` 网络仍具有容器自己的 loopback；可将 MPI 在该私有 namespace 内所需的有界通信作为计算内部通信验证，但不能把它解释成宿主 loopback 或外网访问许可。[Docker none 网络说明](https://docs.docker.com/engine/network/drivers/none/)

SDK 使用明确、受控、大小受限的请求/回执通道，不提供通用 TCP 代理或任意文件读取。文件 IPC 须按 Linux 实际文件语义重新验证符号链接、硬链接、路径穿越、替换竞争及请求重放；Windows 的文件句柄检查不能直接作为 Linux 证据。网络探测须包括外部地址、宿主地址及宿主 loopback 服务；MPI 内部连通与这些拒绝结果分别记录。

### cgroup、资源与生命周期

保持默认四核、Python 与全部内部 ORCA/MPI 进程合计 1024 MB、ORCA MaxCore 每进程 192 MB，以及同一本地执行环境计算并发 1。验证实际 CPU 配额/允许核集合、总内存、swap 和进程数限制；不把 WSL 虚拟机总内存、单个 ORCA 的 MaxCore 或两个各 1024 MB 的容器误写成累计 1024 MB。cgroup 控制器与容器参数的可用性须实测；Docker 默认未设置资源约束，swap 的实际含义也须明确固定。[Docker 资源限制](https://docs.docker.com/engine/containers/resource_constraints/)、[Linux cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

Python 等待内部计算时仍占累计内存与期限。采用单一父 cgroup 或经验证的等价聚合边界，包含 MPI launcher、rank、助手和所有后代；任务不能迁出或改写该边界。内部请求不申请第二份独立环境租约。旧 Windows 路径与新候选不得以不同后端名称绕过同一宿主的环境总额度。

同一 Run 保留唯一协调者；工具注册、输入校验、预算预留、稳定请求键、实际启动、证据归档和结果资格仍走现有责任链。OPI、原生输入及 SDK 不建立三套 Linux 启动协议。本步骤继续限制每次 Python 尝试最多一个新内部 ORCA 请求，不借平台迁移提前实施多计算算法或检查点恢复。

取消、作业/脚本期限、内存超限和协调者消失须覆盖整个聚合进程树。终止 Windows 启动 CLI、关闭终端或依赖容器退出选项都不能替代该证明。接入前必须选定并验证系统级清理机制，特别覆盖宿主协调者硬退出后容器/进程仍可能存在的窗口；清理未确认时不得释放租约或启动副本。必要的检查、停止和收集有自己的期限；文件复制和归档期间也维持控制检查。

### 持久身份、未知状态与证据

启动前先持久化现有预算和意图，记录 backend、发行版/运行时身份、镜像 digest、稳定执行身份、容器 ID（若使用）、cgroup 标识及 Linux PID/启动身份。容器名或 PID 单独不足以识别一次执行。实际成本包含 Python、MPI 与 ORCA 的累计 CPU、内存及时间；信息丢失标为未知，不记为零。

超时未收到运行时响应、WSL/daemon 重启、协调者崩溃及创建与保存句柄之间的断点均先只读对账。未知执行和内部回执保守占用原租约及预算，禁止重跑整段 Python 或换容器名重置调用数。只有准确身份与进程树终止事实确认后才可收集可变文件、结算和释放额度；不能证明的状态继续报告未知。此处要求安全拒绝和事实保留，不承诺本步骤实现后续检查点恢复。

## 验收与交付条件

候选接入后的步骤 2 验收至少覆盖：

- 动态 Python、固定必要库、受控 SDK 与真实四核 ORCA 的单次完整链路；OPI、原生输入和 SDK 复用同一入口。
- 凭据/产品源码/宿主文件/网络拒绝，路径重定向、继承权限及直接启动 ORCA 的实际绕过尝试。
- Python 与内部 ORCA 同时存活时累计资源受限，环境内双 Run 竞争不可绕过并发额度；等待 SDK 不死锁。
- 超时、取消、内存或进程额度超限、协调者硬退出、容器启动回执丢失、WSL/运行时状态不可用时的有界行为；未知状态保留租约和累计预算，不重复启动。
- 真实输入、代码、镜像/依赖身份、原始输出、启动与资源事实可核验；部分归档和科学失败如实保留。缺固定 JSON 不暗中转换或重算，通用观察不自动取得科学资格。

环境探测、合成故障测试、真实 MPI、真实 ORCA 和真实模型证据分别报告；未执行项明确列出。总蓝图对应平台契约与必要定向测试随本次适配同步，仍保持一个现行总蓝图。只有取得实际证据才更新 capabilities 和验收状态，完成后按项目约定提交、推送并报告“等待用户验收”。本 ADR 记录已实现代码与阶段性事实，不把最终生产验收、完整隔离或后续步骤标为通过。
