## 3. 五项最小修复

### R-01：将明确未启动的准备失败正确结算

**问题位置：**[calculation.py](../src/orca_agent/tools/calculation.py) 中的 Artifact 核验、输入生成和 `prepared.json` 写入，发生在现有启动前异常处理范围之外。错误进入协调者后被记为 `unknown`，没有 PID 可供恢复确认，环境唯一额度无法释放。

**最小改法：**

1. 将上述准备操作纳入“尚未调用执行后端”的明确异常边界；只处理能够确定未启动的正常异常。
2. 持久化失败回执：失败原因、`not_started=true`、`handle=null`及已留下的部分文件。
3. 将普通准备失败结算为 **attempt 失败、started=false、Run 失败**，保存事实后释放环境并发额度。
4. 将“未启动的执行事实”与 `Attempt.state="not_started"` 区分。现有协调者会继续处理 `not_started` 尝试，不能让普通准备错误进入这个可恢复分支而自动重试。
5. 暂停导致的执行前阻断保留可恢复语义；取消导致的阻断保持取消语义。
6. 实际 ORCA 启动数保持 0；已有尝试、累计预占和诊断保留。释放环境并发槽不等于退回历史预算。
7. 收集部分文件失败时，追加收集诊断，仍保留“确定未启动”的事实。若连最低持久化记录都无法保存，则报告存储失败并保守保留占用，不能无证据删除租约。

硬崩溃、已进入后端但启动事实不明等情况，继续按原规则对账；缺少 PID 本身仍不是释放额度的依据。

**必须回归：**

- 分别在几何核验、输入生成、准备回执写入处注入可处理异常：后端调用为 0，失败事实存在，环境额度释放。
- 恢复同一失败 Run 两次：没有自动重试，实际启动数和累计尝试记录不变。
- 另一合法 Run 能获取同一环境额度。
- 部分文件已写入后失败、后续收集也失败：保留文件与诊断，不伪造未知进程。
- 原有硬崩溃和启动句柄丢失测试仍保留未知占用。

### R-02：让 SCF 收敛、几何和能量属于同一计算片段

**问题位置：**[adapter.py](../src/orca_agent/orca/adapter.py) 的 `scf_ok` 只比较全文件中的行号先后，允许不同优化周期的证据被组合。

**最小改法：**

1. 在现有解析器内，为待发布能量识别所属的几何/SCF 计算片段，同时保存片段定位、坐标来源、收敛标记和能量行号。
2. 只使用同一片段内的收敛或失败证据；不从全文件分别取“最后一次出现”再拼接。
3. 保持以下三态：同片段明确收敛为 `passed`，明确不收敛为 `failed`，缺少足够证据为 `unverified`。来源冲突或片段无法唯一绑定时拒绝发布。
4. 同步修改诊断：缺少收敛标记不能直接描述为实际发生了 SCF 不收敛。
5. Opt 迭代耗尽时，仍允许发布经自身检查通过、绑定具体结构的局部能量；不得发布收敛优化结构。最终能量缺证据时，不静默用上一周期能量冒充。
6. 当前片段选择同时覆盖无 JSON 和已有一致 JSON 两种路径；JSON/text 冲突仍保守拒绝，读取仍禁止转换或计算。

**必须回归：**

- 现有真实 SP、严格 Opt 输出回放仍通过。
- 多周期 Opt 的最后一次 SCF 成功标记被移除：最终能量不得借用前周期通过，检查为 `unverified`。
- 前周期成功、当前周期明确失败：当前能量检查为 `failed`。
- Opt 限次但当前周期 SCF 合格：保留局部能量及其结构/行号来源，不发布优化结构。
- 一致 JSON、缺 JSON、冲突 JSON 均覆盖，且文件 hash 不变、外部程序启动为 0。

同步补强 [test_science.py](../tests/live/test_science.py) 中 `water_opt_limit` 的断言：除“不存在优化结构”外，还须检查预期局部能量存在及来源绑定。现有分支绕过了 `outputs == expected`，不能继续遗漏该保证。

### R-03：恢复后补收证据，并保留旧结果

**问题位置：**[runner.py](../src/orca_agent/runner.py) 的 `_recover()` 无条件复用已有 Result。首次状态未知时保存的 Result 没有 Artifact；即使后来确认终止，也不会再收集目录中的 stdout 等文件。

**最小改法：**

1. 区分“已完成收集的结果”和“等待终止确认的 unknown 结果”。进程仍不明时不归档正在变化的文件；确认终止后进行有界收集和读取。
2. 保留旧 Result 与执行回执原字节；追加新的恢复 Result，记录终止依据、原始 Artifact/hash、可读取观察和诊断。
3. 为 Result 增加一个可选的显式替代关联，如 `supersedes_result_id`，默认空以兼容旧数据。它只是 Result 的局部字段，不增加新领域对象。
4. 结果选择只接受身份一致、替代关系合法且具有唯一末端的结果。多个无关联候选、循环或跨 attempt 关联仍报错，禁止按文件时间挑“最新结果”。
5. 保存顺序固定为：**Artifact → 新 Result → 原子更新 Run 中的当前 result_id 与完整历史引用 → 结算/释放额度**。
6. 恢复时先检查是否已有合法的新结果尚未绑定到 Run；验证后直接接回，避免再次生成结果或再次启动计算。
7. 覆盖已有 `finished_at`、但当前结果仍是空 unknown Result 的历史状态。对此只补收并更新引用，不再次调用会重复结算的路径。
8. “进程已停止”只提供终止证据，不提供科学成功证据；没有可靠完成事实时，恢复结果保留观察和限制，不发布合格科学输出。

**必须回归：**

- unknown Result 已保存，目录有 stdout/stderr：确认终止后可以通过证据接口读取归档，新旧 Result 均保留。
- unknown Result 尚未保存便中断：同样能补收，不虚构旧结果。
- 新 Result 已保存、Run 尚未更新时再次崩溃：恢复接回已有结果，不出现多结果歧义。
- Run 已更新、额度尚未释放时再次崩溃：安全释放，结果不变。
- 连续两次以上 resume：没有新增科学启动、重复成本或无限追加恢复结果。
- 已结算但仍指向 unknown Result 的旧状态可补收；已有耗时/CPU 下界与未知用量标记保持。
- 缺失/损坏文件、无关联的多个结果仍留下明确诊断，不形成伪成功。

### R-04：让离线取消与在线取消保持一致

**问题位置：**[runner.py](../src/orca_agent/runner.py) 在对账前后控制文件未变化时清空动作，没有区分原动作是 `pause` 还是 `cancel`。

**最小改法：**

1. 对账后在控制锁内重新读取动作；待处理的 `cancel` 优先于继续计划。
2. 已确认没有活动计算时，保存取消状态，不启动剩余 Step，并保留取消记录。
3. 终止仍未知时保留未知状态、取消请求和额度；不能为响应取消而宣称计算已停止。
4. 只清除本次 resume 对应且在对账期间未改变的既有 `pause`。
5. 恢复期间新到达的 pause/cancel 继续生效；已完成 Run 的历史完成事实不因迟到信号被改写。

**必须回归：**

- 两步 Run 完成第一步后暂停，协调者退出，再 cancel → resume：总启动数保持 1，Run 为 cancelled。
- 重复 resume 仍不执行第二步，预算与第一步结果不变。
- 普通 pause → resume 能继续；恢复期间新增控制信号不丢失。
- 取消时终止未知：占用保留，没有新启动。
- 原有在线取消测试继续通过。

### R-05：统一已启用的 ORCA 版本判定

**问题位置：**[doctor.py](../src/orca_agent/doctor.py) 接受 `>=6.1.1`，而 [adapter.py](../src/orca_agent/orca/adapter.py) 仅接受 `6.1.1`。

**最小改法：**

1. 提取一个轻量、无执行副作用的共用版本声明及判定函数，供环境探测、科学执行准入和输出检查使用；当前启用范围精确保持 `6.1.1`。
2. 区分第三方最低兼容要求与本项目已经验证、允许执行的版本。未启用版本在预占科学尝试和启动前拒绝。
3. 保留完整版本 token，不把未知后缀截掉后当作已验证版本；缺失或含混版本按未验证处理。
4. 输出版本必须与冻结环境相符。原有可执行文件 hash 校验继续保留。

**必须回归：**

| 版本证据 | 预期 |
| --- | --- |
| `6.1.1`，含正常 RELEASE 描述 | 前后门禁一致通过 |
| `6.1.0`、`6.1.2`、`6.2.0` | 执行前拒绝，科学启动为 0 |
| `6.1.1-f.1` 等未启用后缀 | 保留原值并拒绝 |
| 缺失、重复或无法唯一识别的版本 | 未验证或明确拒绝 |
| 输出与冻结环境版本不一致 | 不发布合格输出 |

这些反例使用模拟探测和真实输出的临时副本验证，不安装或运行其他 ORCA 版本。

## 4. 检查版本与历史兼容

R-02 改变了检查器的实际判定行为，新增检查结果使用 `orca-hf-2`，以便与历史结论区分。此处只做必要的版本兼容，不建设通用迁移框架。

- 新建 Request 的最低检查、科学 Tool 声明和新生成 Check 使用同一当前版本；需同步 `structured.py`、`models.py`、注册表和检查代码，不能只改一个默认值。
- 数据模型仍能读取 `orca-hf-1`。历史文件省略字段时不得被新默认值解释成新版；新建对象显式填写当前规则版本。
- 历史 Request/Result 的版本、字节、ID 和原检查结论保持不变。新版回放生成独立不可变复验记录，关联原 Result、Artifact/hash、源码版本和差异。
- 历史 Run 仍允许查看、取消、安全对账和补收。未完成旧 Run 若需继续科学执行，应在新尝试预占之前明确提示需要规则复验；本次不承诺无缝迁移，也不能创建新 Run 或改 ID 来逃避原预算。
- 当前规则的目标与下游消费不能把旧版 `passed` 自动当成新版通过。版本不匹配应有明确诊断，不用字符串排序推测兼容性。

需新增版本回归：旧数据可读且不改写；新 Request/Tool/Check 一致绑定新版；旧合格输出不能直接满足新规则；规则不匹配仍允许清理、收集，不能触发计算。

用一份简短的 `docs/decisions/` 记录说明检查版本升级和恢复 Result 替代关联，满足总蓝图对科学保证与对象关系调整的可追溯要求。

### 5.2 回放真实历史产物

使用修复后的读取器检查现有 H₂O/CH₄ SP、严格 Opt、Opt→SP、SCF 失败、Opt 限次和早期替代停止样例。旧文件只读，逐项记录新规则检查、源文件 hash、差异和当前适用性。

**按本方案限定的修改范围，必需新增 ORCA 启动为 0 次。** 输入方法、计算参数、后端进程创建和 MPI 管理保持原实现，依靠定向故障测试及真实产物回放验证修复。若实施中实际改变输入生成内容或后端启动/清理机制，应追加受影响的真实验证；至少可用一条受控 Opt→SP 做科学冒烟，生命周期改动另补对应真实场景，不以原计划的“0 次”掩盖新增验证需要。

### 5.3 完整离线回归

修复后执行一次全套离线测试与 Ruff，并记录新增通过数及所有跳过原因：

```powershell

```

默认测试继续禁止网络及科学程序启动。原有未知占用、防重复、进程清理、hash 和只读边界测试必须继续通过，不得通过删除断言或放宽科学门槛消除失败。
