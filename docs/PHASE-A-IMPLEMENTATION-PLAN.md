## 1. 第一阶段要交付什么

交付一个**不依赖 LLM、能在本地受控执行真实 ORCA 单点计算（SP）和几何优化（Opt）、保留可追溯证据的最小运行底座**。

阶段结束时，开发者应能用结构化请求完成：

```text
结构化 Request + 明确的 Plan/Step
  → Tool 参数、文件、许可和预算校验
  → 固化输入并保存启动意图
  → OPI 构造输入 + 受管本地后端执行 ORCA
  → 收集原始产物 + 统一读取
  → 对每个输出进行确定性科学检查
  → 保存 Result/Artifact + 输出结果清单
```

同时证明：真实失败不会变成伪成功；初始结构不会被覆盖；资源和尝试次数有上限；暂停、取消、进程异常退出和恢复不会造成重复计算。

**阶段 A 完成后具备的是可供 Agent 调用的计算底座。自然语言理解、模型规划和自主反馈能力在阶段 B 接入。**

## 2. 范围与实施假设

### 2.1 本阶段范围

| 类别 | 本阶段实现范围 |
| --- | --- |
| 输入 | 明确的 XYZ 几何、总电荷、多重度及受限方法配置；由结构化文件或测试代码提供 |
| 科学能力 | 一个经验证的方法/基组组合下的 SP 与无约束 Opt；先从小型闭壳层分子开始 |
| 工具边界 | 单一注册表、参数 schema、影响声明、检查规则和固定实现入口 |
| 运行时 | 七个最小领域对象；固定 Plan 的执行与生命周期管理 |
| 执行环境 | 只验收一种实际本地环境，前台 CLI 为唯一协调者 |
| 证据 | 原始输入、输出、旁文件、结构、hash、来源和逐输出检查 |
| 文件读取 | 为验收提供有界、受控的已有产物查看；统一读取器不得隐式执行 |
| 可靠性 | 累计预算、环境全局并发、受管进程树、暂停/取消、故障对账和显式恢复 |
| 交付 | 确定性结果清单、能力范围、测试记录及真实计算证据 |

本阶段不建设 LLM/API 接入、自然语言对话、自动计划修订、自动科学修复策略、远程服务器/Slurm、Web UI、数据库、事件总线、多 Agent 平台、完整知识库，也不展开 Freq、热化学、光谱、构象、TS/NEB/IRC 能力。

外部历史结果导入、开放字段发现、跨结果科学分析的产品功能留给阶段 B；阶段 A 先确保底层文件读取、来源记录和科学状态能够被它们复用。

## 4. 逐项任务说明

### A-01：建立最小工程与开发约定

**目标：**让后续代码有统一入口、依赖锁和验证方法，避免先建立大量空框架。

**工作内容：**

1. 以当前目录作为项目根目录，建立 `src/orca_agent/` 包和 `pyproject.toml`。
2. 创建独立虚拟环境，选定已验证的 Python 3.11 或更高版本；用 `uv.lock` 固定依赖。
3. 添加实际需要的 Pydantic、pytest、Ruff；OPI 精确版本在 A-02 核对后锁定。
4. 编写 README、配置示例和 `.gitignore`，排除环境、凭据、运行缓存及不适合入库的大型计算产物。
5. 实施时将总蓝图保存为项目内唯一现行基准，在 AGENTS.md 中引用其开发原则；阶段任务继续由本文管理。
6. 配置离线单元/集成测试与真实 ORCA 测试标记。默认离线测试禁止网络和外部科学程序启动，真实测试需显式开启。

**交付物：**最小可安装包、依赖锁、README、开发约定、配置示例和测试入口。

**验收条件：**在依赖已安装的环境中可执行项目帮助、Ruff 和离线测试；缺少 ORCA 时仍可运行离线检查；真实测试的缺环境状态明确显示为跳过/未验证。

### A-02：探测本地环境并冻结首批验收样例

**目标：**先确定实际可运行的版本组合和验收依据，再开发科学适配。

**工作内容：**

1. 提供只做环境诊断的 `doctor` 入口，记录 OS、Python、OPI、ORCA 可执行文件绝对路径、版本、MPI、工作目录可写性和可用资源。
2. 版本探测不提交科学计算；无法通过无计算方式确定的字段标记为待验证。
3. 锁定兼容版本。OPI 官方目前说明，2.0 及以上版本要求 ORCA 至少为 6.1.1；最终以所锁版本要求和本机实测为准。[OPI 官方仓库](https://github.com/faccts/opi)
4. 按平台核对并行依赖。ORCA 手册区分 Windows 的 MS-MPI 与 Linux/macOS 的 OpenMPI，且要求用完整路径调用 ORCA driver，由其启动并行模块。[ORCA 并行说明](https://www.faccts.de/docs/orca/6.1/manual/contents/essentialelements/parallel.html)
5. 记录第三方版本及许可证来源；不把 ORCA 安装包当作项目自带依赖。
6. 冻结 SP 正例、Opt 正例、SCF 不收敛和优化未收敛样例的输入条件及预期行为；限制支持范围为明确的一组小体系和方法配置。
7. 提前确定独立参考或专家核验方法：可采用人工审阅的标准输入及原始输出、可信公开参考，或独立检查。数值容差依据同一物理量、方法、几何和版本条件制定，不能从被测程序结果反向生成标准答案。

**交付物：**环境报告、版本清单、首批用例清单和参考/容差说明。

**验收条件：**能明确回答“安装了什么、支持哪个本地执行环境、什么尚未验证、首批用例如何判定正确”。版本探测通过不等于真实计算或并行能力通过。

环境缺失不阻止 A-03/A-04 的离线开发，但真实计算和阶段验收必须保持未验证状态。

### A-03：定义最小七对象与 Tool 契约

**目标：**让 SP 和 Opt 通过同一套类型、校验和调用规则进入执行链。

| 对象 | 阶段 A 最少需要的内容 |
| --- | --- |
| Request | 输入依据、体系/结构引用、电荷、多重度、方法与条件来源、目标与最低检查、版本 |
| Plan | Request 版本、显式 Step 列表及依赖、目标到输出端口的映射、版本 |
| Step | Tool 标识、类型化参数、输入引用、逻辑步骤身份和前置检查 |
| Tool | 参数 schema、兼容组合、输入/输出角色、影响、资源、检查版本、固定实现 |
| Run | 当前引用、许可快照、状态、尝试、预算、执行身份和协调信息 |
| Result | 执行事实、逐输出检查、合格输出、证据观察、诊断与来源 |
| Artifact | 文件身份、角色、位置、hash、来源、所属尝试或独立导入来源 |

**工作内容：**

1. 注册 SP、Opt 两个科学 Tool，名称在实现时统一固定；禁止通过任意字符串透传 ORCA 输入或可执行代码。
2. 从同一 Tool 定义导出参数说明和校验，不维护互相独立的“文档 schema”和“执行 schema”。
3. 建立结构化请求入口：由代码或用例文件显式提供科学条件，由程序生成持久 ID、受控路径和状态。
4. 校验原子数量/元素、有限坐标及单位、电荷、多重度、电子数基本合法性、允许的方法组合、资源和文件范围。电子数奇偶性不能替用户选择自旋态。
5. 静态 Plan 支持最小依赖校验和明确输入绑定；未来输出引用绑定生产 Step/端口，执行前再固化到具体尝试和 Artifact。
6. 分开记录执行状态、科学检查状态、目标状态和交付状态；科学检查至少区分通过、未通过、未验证、不适用。

**交付物：**最小数据模型、工具注册表、参数契约、结构化用例和校验测试。

**验收条件：**错误电子态、缺少结构、未注册工具、非法参数组合、循环依赖、越界引用和超资源请求均不能启动计算；程序不提供任意 shell/Python 执行入口。

### A-04：实现文件存储、预算与环境全局额度

**目标：**在启动外部程序之前，先把“算什么、允许算几次、证据归谁”保存清楚。

**工作内容：**

1. 每个 Run、Step、attempt 使用稳定身份和独立目录。输入几何使用 `geometry.xyz` 等名称，与 ORCA 作业 basename 分离。
2. 保存不可变 Request/Plan 修订、输入指纹、许可快照和文件来源；初始几何及已归档证据不得原地覆盖。
3. 原子写入单个文件；先保存完整产物与不可变对象，再更新 Run 当前引用。恢复时检查引用完整性和孤立产物。
4. 将预算上限、已预占额度和累计实际用量分开保存。启动前持久化预算占用及启动意图；未知状态保守占用，只有证明未执行或已释放才按规则结算。
5. 使用 Run 协调锁保证同一 Run 只有一个推进者；另设执行环境共享额度与必要锁，覆盖所有 Run/CLI 进程。
6. 环境额度按稳定环境身份定位，不能因为换 Run、换工作目录或释放旧协调锁就获得新的计算名额。
7. 将检查失败、预算拒绝和文件拒绝保存为可追溯事实；预算耗尽仍允许有界清理、收集和确定性交付。

**交付物：**文件存储函数、原子更新/锁、预算核算、环境额度记录及定向测试。

**验收条件：**重复调用不覆盖旧尝试；重启后用量仍在；同一 Run 的第二协调者不能推进；两个 Run 不能绕过环境并发上限；状态未知的旧尝试继续占用额度。

### A-05：实现受管理的本地执行后端

**目标：**具备真实计算所需的启动、查询、停止、收集和对账能力。

**工作内容：**

1. 后端仅接受固化输入、受控工作目录和资源配置；统一处理 ORCA 及经登记的后处理程序，不接受调用者提交任意脚本。
2. 保存程序路径、参数列表、工作目录、启动时间、PID/创建时间、启动身份、退出码、stdout/stderr 和资源记录。
3. 在启动前建立系统级进程管理。Windows 可优先验证 Job Object：进程需先纳入管理再执行，避免创建后尚未受管的窗口；核验 MPI 派生进程是否全部纳入。
4. 验证协调者消失后终止受管计算的机制，包括句柄继承、子进程逃逸和异常启动窗口。Windows 的关闭最后句柄时终止进程组机制可作为实现依据，但必须通过本机测试。[Microsoft Job Object 限制说明](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)
5. 落实核数与进程树总内存约束，并记录计量口径。Windows JobMemoryLimit 针对组内进程的提交内存，不能把它与任务管理器工作集混为同一指标。[Microsoft 内存限制说明](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)
6. 实现每次作业期限、取消及清理超时；先用会派生子进程的本地测试程序验证管理能力，再放开真实 ORCA。
7. 前台 CLI 正常退出前停止新提交并完成明确的暂停/取消处理；异常退出由系统机制收束受管计算。新启动只显示事实，显式 `resume` 才允许对账后推进。

**交付物：**`backends/local.py`、平台决策记录、测试子进程及生命周期/资源测试记录。

**验收条件：**取消和强制终止协调者后没有遗留的受管计算子孙进程；超资源和超时有确定结果；不能只凭 `%maxcore` 配置、`finally` 清理或杀掉父 PID 宣称通过。

初步测试通过后可进入 A-06；真实 ORCA/MPI 的进程覆盖和清理证据在后续真实测试中补齐，缺失时 A-10 不得通过。

### A-06：打通 OPI 适配和首个真实 SP

**目标：**获得第一条完整、可复算、可定位来源的真实科学结果。

**工作内容：**

1. 在唯一 `orca/adapter.py` 中明确输入构造、执行接入、已有产物读取和受控后处理的边界；本地执行统一交给 A-05 后端。
2. 为 SP 显式定义需要的产物与字段，不把全部 ORCA 模式都假定为必须生成相同 JSON。
3. 如所需 JSON 必须经转换生成，将转换定义为独立、已登记且有预算的后处理动作；不得借解析函数暗中执行。
4. 使用 A-02 冻结的输入，经 Tool → 适配器 → 后端完成真实 ORCA SP。
5. 统一提取能量、单位、收敛证据、结构/电子态和方法条件；同一适配器中规定数据来源优先级与冲突处理。
6. 科学检查覆盖 SCF 收敛、有限数值、能量含义/单位、正确结构与电子态、请求输出存在及产物来源一致。
7. 输出 Result/Artifact 和确定性结果清单，关联原始文件、字段/行号、规则版本及环境版本。

**交付物：**SP Tool、OPI 适配器、SP 检查规则、一份真实成功证据包和可复现入口。

**验收条件：**真实 SP 输出通过明确检查，并按 A-02 的独立依据核验；每个报告数值均可追溯；仅退出码为 0、存在能量文本或出现正常终止标记不能单独判为科学通过。

### A-07：加入真实 Opt 并保护初始结构

**目标：**复用 SP 的公共执行链，正确交付优化收敛结构及其适用范围。

**工作内容：**

1. 增加 Opt 的局部参数、最大迭代数、预期产物和检查规则；复用注册表、适配器、后端、存储及预算。
2. 以明显偏离平衡结构但合理的小分子作为固定初始输入，运行真实无约束优化。
3. 分别记录初始几何、最终几何及可用的迭代信息；运行前后核对初始几何 hash。
4. 检查优化是否按所选判据收敛、最终结构/原子顺序/电子态是否一致，以及最终能量与结构是否属于同一计算阶段。
5. 为能量和优化结构分别保留检查状态。优化失败时，已有能量只有满足自身规则且绑定具体结构/迭代才可作为合格的局部结果。
6. 用静态 `Opt → SP` 小用例证明：消费者使用具体生产尝试的合格结构；优化未通过时，不能把最后一帧当作“已收敛优化结构”传下去。

**交付物：**Opt Tool、优化检查、初始几何保护测试、真实优化证据和静态依赖用例。

**验收条件：**成功结构和未收敛结构明确区分；输入原件不变；下游不按“最新文件”选取结构；不为 Opt 另建一套执行器。

本阶段未验证 Hessian/频率，因此交付表述限定为“按指定优化判据收敛的结构”。极小值或一阶鞍点性质还需相应 Hessian 证据，不能把优化收敛直接写成无虚频极小值或全局最稳定结构。[ORCA 几何优化手册](https://www.faccts.de/docs/orca/6.1/manual/contents/structurereactivity/optimizations.html)

### A-08：收集真实失败并验证只读和部分结果边界

**目标：**失败时仍保留事实，读取证据时保持执行边界。

**工作内容：**

1. 使用真实 ORCA 产生并保存至少一个 SCF 不收敛和一个 Opt 达到迭代上限仍未收敛的输出；可使用受控较小迭代上限，但须确认输出确实呈现目标失败。
2. 区分输入拒绝、启动失败、科学未收敛、超时、取消、产物缺失/损坏、解析冲突及执行状态未知。
3. 诊断包含错误类别、证据位置、影响的输出和停止原因；修复建议如有，仅作为受限候选，不自动开放执行。
4. 失败结果不发布不合格科学端口；已存在的局部证据按来源与验证状态保留，不因最终失败被整体删除。
5. 同一逻辑步骤的新尝试使用独立目录并累加预算；验证无有效变化的重复失败可以停止。本阶段不要求模型挑选修复并重跑。
6. 统一读取器显式禁用 OPI 创建缺失 JSON 和重写已有 JSON 的行为；按已有文件选择读取项。OPI 2.0 的 `Output.parse()` 默认可能创建缺失 JSON，不能直接把默认调用当作只读。[OPI Output API](https://www.faccts.de/docs/opi/2.0/docs/contents/api/opi/output/core/index.html#opi.output.core.Output.parse)
7. 为本阶段证据检查提供 Artifact 引用、有界文件列表/文本片段及已知字段读取。缺文件时报告事实和所需后处理，不启动转换或 ORCA。

**交付物：**真实失败 fixtures、结构化诊断、部分结果规则和只读副作用测试。

**验收条件：**真实失败保留全部原始文件和成本；非合格数据只能作为明确标记的观察；只读检查前后科学文件清单/hash 不变，且无外部程序启动，调用审计记录除外。

### A-09：验证启动窗口、暂停/取消与恢复

**目标：**用具体故障证明底座不会重复启动、错误放行资源或丢失历史事实。

**工作内容：**

1. 在保存启动意图、创建进程、保存句柄、保存 Result、更新 Run 引用等位置提供仅用于测试的故障注入点。
2. 依照第 7 节矩阵测试协调者被强制结束、双客户端竞争、PID 复用、预算边界、缺失产物和过期版本。
3. `pause`：不启动后续步骤；当前作业在原期限内完成并收集后停下。
4. `cancel`：请求停止受管计算并核实整个进程树；未确认终止时保留未知/待确认状态和资源占用。
5. `resume`：先核实历史尝试、进程身份、产物完整性、当前条件、累计用量和额度，再决定继续、收集或报告无法确认。
6. 在同一协调锁内、实际提交前再次核对 Request/Plan/许可版本及暂停/取消状态；过期提案必须重新校验，不能只换版本标签。
7. 恢复不自动清零预算，不保证 ORCA 断点续算，不因缺少已保存句柄直接新建替代计算。

**交付物：**可靠性测试、故障记录、恢复说明和残留进程/额度核查证据。

**验收条件：**关键故障窗口均有可复现测试；可确认状态正确恢复，不可确认状态保守停止；未发生重复执行、误杀无关进程、提前释放额度或覆盖旧证据。

### A-10：整理能力证据并交付阶段 A

**目标：**让后续阶段能判断底座实际支持什么，并可重复验证。

**工作内容：**

1. 完成统一 CLI 的帮助和示例，建议入口包括 `doctor`、结构化 `run`、`status`、`pause`、`cancel`、`resume` 和受控 `inspect`；这些是待实现接口，不是现有命令。
2. 整理 `capabilities.md`：按版本/体系/参数组合分别记录输入可构造、可执行、可解析、可科学验证、目标可完成、自动修复证据。
3. 本阶段自动修复、模型规划、远程执行等栏目明确写未实现/未验证，不能用一个 `supported: true` 替代分项状态。
4. 完成阶段验收清单，关联真实成功、真实失败及离线可靠性证据；附成本、跳过项、限制和复现步骤。
5. 运行所改模块的必要回归检查；核对代码、配置、文档和实际支持范围一致。
6. 按已明确的仓库约定记录提交；只有已指定远端并具备发布授权时才推送。当前方案不假定存在远端，也不包含本轮推送动作。

**交付物：**可运行代码、锁定依赖、测试结果、真实证据索引、能力矩阵、复现说明和阶段验收报告。

**验收条件：**第 8 节全部必需项有证据，交付状态记为“等待用户验收”；用户接受后才记录阶段通过。

## 5. 资源与预算基线

### 5.1 沿用蓝图的资源约束

| 项目 | 阶段 A 基线 | 要证明的事实 |
| --- | --- | --- |
| 本地计算核数 | 最多 4 核 | 实际执行范围受约束，记录 CPU/线程/MPI 设置 |
| 总计算内存 | 1024 MB | 对受管计算进程树落实总量限制并记录计量口径 |
| ORCA MaxCore | 每进程 192 MB | 输入正确传递；它不能替代进程树总内存约束 |
| 环境全局计算并发 | 1 个 | 多 Run、多 CLI、不同项目工作目录不能绕过同一环境额度 |

首个调试计算可以显式选择串行配置，但只能证明串行能力。若阶段交付宣称 4 核并行已支持，必须补充真实 4 核 ORCA/MPI 成功与受管清理证据；原定 4 核 profile 未验证时不能写为通过。

### 5.2 建议的开发预算

下列是首批小体系测试的配置起点，不是已授权执行，也不是永久科学限制。在 A-02/A-04 固定，任何调整都要有记录，不能在失败后悄悄放宽。

| 项目 | 建议上限/规则 |
| --- | --- |
| 每个逻辑科学步骤 | 最多 3 次尝试；默认不自动重试 |
| 每 Run 的 ORCA 总启动 | 最多 4 次；与每步上限同时生效 |
| 每 Run 的额外 ORCA 启动 | 最多 3 次，且仍受总启动上限约束 |
| 后处理启动 | 首版默认 0；具体能力需要转换时显式配置有限上限并单独计数 |
| SP 作业期限 | 建议 300 秒 |
| Opt 作业期限 | 建议 900 秒 |
| Run 执行总时限 | 建议 1800 秒，保存计时依据；恢复不得重置 |
| 取消确认 / 产物收集 | 分别设有限超时，建议各 30 秒；失败保留待确认事实 |
| 证据读取 | 显式字节数/行数/数组切片上限及读取超时；默认禁止全量大文件返回 |
| 模型调用、自主计划修订 | 阶段 A 不启用 |

ORCA 内部 SCF/Opt 迭代要有明确上限；一次 Tool 调用包含的工作量也要计入期限和实际资源。预算耗尽阻止新计算，但不阻止必要的有界取消、收集和结果清单生成。
